## Implementation Notes
- Mongoose builds indexes asynchronously; any test that calls `.create()` right after importing a model with a `unique` index must `await Model.init()` first, or duplicate-key rejection tests will be flaky (discovered in 1.3, relevant to 3.x BadgeGrantService tests too).
- Task 3.4 (BadgeGrantService) must add `badgeSummaryCached?: IUserBadgeSummaryEntry[]` to `packages/core/src/interfaces/user.ts`'s `IUser` before writing to that field from TypeScript; the Mongoose schema field itself (task 1.4) has no `IUser` type counterpart yet, and its array subdocuments auto-generate an `_id` (consider `_id: false` when task 3.4 writes to it).
- `findByIdAndUpdate(..., { runValidators: true })` does NOT invoke a Mongoose model's `pre('validate', fn)` document middleware (only schema-level path validators run) -- empirically confirmed on this repo's Mongoose 6.13.9 during task 2.1. Any service using `findByIdAndUpdate` for a document with custom cross-field validation logic must re-run that validation at the service layer explicitly.
- `IBadgeTypeHasId` is defined and exported from `badge-type-service.ts` (not `interfaces/badge.ts`) -- import it from there in tasks 2.2/5.1 rather than redefining.
- The `crowi.events.activity` `'updated'` event's `ActivityDocument.user` field is NOT populated at emit time (`createByParameters` never `include`s the user relation, unlike `updateByParameters`) -- use the scalar `activity.userId` field instead, never `.user`, when consuming this event elsewhere.

Task 5.2 (user-badge apiv3 route, the first real caller of `grantManualBadge`) MUST either pass `crowi` on every call, or better, this should be tightened to a *required* parameter across `evaluateAndGrantForUser`/`grantManualBadge`/`recordBadgeGrant`/`emitBadgeGrantActivity` so a missing `crowi` is a compile error, not a silent requirement-5.1 gap. Update the 17 pre-3.4 tests that don't pass `crowi` to pass an explicit test double when this is tightened.
- **Follow-up (not blocking)**: `IUserBadgeSummaryEntry` is currently duplicated (manually synced) between `apps/app/src/features/user-badge/interfaces/badge.ts` (task 1.1) and `packages/core/src/interfaces/user.ts` (task 3.4). Any future field addition to `IUserBadgeSummaryEntry` must be mirrored in that Mongoose schema, and the only way to catch a missed mirror is to assert on DB-refetched state (`User.findById(...)`), never on the in-memory object passed into the save call.

- **PRODUCTION HOTFIX (post-13.8, found via real user report)**: `badge-type.ts`'s `validator.create`/`validator.update` express-validator chains never referenced `iconType` at all (confirmed via a zero-hit grep before the fix) -- `iconKey` was required unconditionally on create and required-if-present on update, so every real admin-form submission choosing "画像アップロード" (which sends `iconKey` as an empty string, not omitted, alongside `iconType: 'image'`/a file) was rejected with a false "iconKey is required" 400, even though the entire rest of the image-icon pipeline (13.1-13.7) was correct. Task 13.8's own e2e test never caught this because it always sent a non-empty `iconKey: 'star'` even in its image-icon test cases -- a test fixture that avoids the exact shape a real client submission takes will not catch a validator gap like this. Fixed by making the `iconKey` rule conditional (`.if(iconType !== 'image')` on create, `.if(req.file == null)` on update) and adding an `iconType` enum validator. Lesson: an "end-to-end" test that hand-constructs its own request body instead of mirroring the REAL client's exact field-by-field submission shape (including which fields get sent as empty string vs. omitted) can pass while the real UI is completely broken -- for admin-form-driven apiv3 routes, prefer asserting against the actual client component's serialized output (or as close to it as practical) over an independently-authored "plausible" fixture.
- **Follow-up (not blocking, noted by hotfix review, not yet implemented)**: submitting `iconType: 'image'` with no file attached and no `iconKey` (reachable if an admin selects "画像アップロード" but forgets to choose a file) currently falls through to a generic HTTP 500 rather than a clean 400, because the route drops `iconType` before forwarding to the service and Mongoose's own `iconKey` `required` validator throws a bare `ValidationError` the route's catch block doesn't specifically handle. No data corruption occurs (the BadgeType is never created), but the error message is unhelpful. A future task should add `required` to `BadgeTypeForm.tsx`'s image-file `<input>` and/or map bare Mongoose `ValidationError` to a proper 400 in the route's catch block.
- **PRODUCTION HOTFIX (post-13.8, found via real user report -- browser console log, not server logs)**: `packages/ui/src/components/UserPicture.tsx`'s per-badge DOM id was built directly from React's `useId()` (`const badgeIdPrefix = useId();`), which deliberately returns colon-containing ids (e.g. `:r1g:`) so they can never collide with author-chosen ids. `UncontrolledTooltip`'s `target` prop, when given a plain string, is resolved by `reactstrap`'s `findDOMElements` via a raw `document.querySelectorAll(target)` call (confirmed by reading `reactstrap`'s actual source) -- a colon in a CSS ID selector is invalid syntax, so the FIRST real tooltip mount for ANY badge (this bug is not image-icon-specific -- it affects every badge, including plain Material Symbols/emoji ones) threw `SyntaxError: '...' is not a valid selector`, which React/Next.js surfaces to the user as a full-page "client-side exception" crash (commonly described as "500" by a non-technical reporter, even though the server never returned one -- ALL server logs for the affected requests showed clean 200s, confirmed by an exhaustive log audit finding zero 5xx responses in the container's entire history). This bug has existed since badge tooltips were first built (task 4/10.3) but was invisible until now because (a) every existing `UserPicture` test mocks `UncontrolledTooltip` via `next/dynamic`, so none of them ever exercised the real Popper/selector-based lookup, and (b) no real badge data reached any real browser page until tasks 12/13 wired the display sites end-to-end this session -- i.e. this is the SAME class of gap as task 12's original NO-GO finding (a feature whose pieces are all individually tested but whose real end-to-end path was never exercised), just discovered one layer deeper (inside a shared `packages/ui` component) after task 12's own gap was already closed. Fixed with `useId().replace(/:/g, '')`, verified collision-safe (uniqueness comes from React's internal counter, not the colon characters) via the pre-existing multi-instance uniqueness test. Lesson: any test that mocks out a real DOM-selector-consuming library (tooltip/popper/modal-positioning libraries are common offenders) should periodically be cross-checked against the REAL library at least once, since a mock can hide a real integration bug indefinitely -- especially one that only manifests in a genuine browser DOM (jsdom's `querySelectorAll` IS strict enough to catch this specific bug if exercised un-mocked, confirmed during this hotfix's review, so the gap was specifically the MOCK, not a jsdom/environment limitation).
